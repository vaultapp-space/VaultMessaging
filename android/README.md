# Vault for Android

A [Capacitor](https://capacitorjs.com) wrapper around the same Svelte web
client (`client/`) that runs on vaultapp.space — not a second native client.
That's deliberate: it's what lets this app keep full E2EE (Double Ratchet,
X3DH, Sender Keys) with zero extra crypto work, unlike `ios/`, whose Swift
client never got the ratchet ported and stays cloud-chats-only.

Distribution is self-hosted only: no Play Store, no official f-droid.org
listing. See "Distribution" below.

## Building it

```bash
export JAVA_HOME="/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home"
export ANDROID_HOME="/opt/homebrew/share/android-commandlinetools"
export PATH="$JAVA_HOME/bin:$ANDROID_HOME/platform-tools:$ANDROID_HOME/cmdline-tools/latest/bin:$PATH"

cd client
npm run build          # builds dist/
npx cap sync android    # copies dist/ into android/app/src/main/assets/public/

cd ../android
./gradlew assembleDebug     # unsigned, for sideload-testing on a dev device
./gradlew assembleRelease   # signed (see Signing below), for real distribution
```

`android/` is plain Gradle/XML/Kotlin — unlike `ios/.xcodeproj` (XcodeGen-
generated, not committed), it's meant to be committed and hand-edited.
Build output (`android/app/build/`, `android/build/`, `android/.gradle/`) and
`android/app/src/main/assets/public/` (a copy of `client/dist`, re-derived by
`cap sync` every time) are gitignored.

## The origin-spoofing trick

`client/capacitor.config.ts` sets `server.hostname` to `app.vaultapp.space`
— a subdomain that never resolves in real DNS and nothing ever connects to.
It exists purely so the WebView's *reported origin* for locally-bundled
assets is a subdomain of `vaultapp.space`, which satisfies the `sameSite:
'strict'` session cookie's same-*site* check, while `client/src/lib/api/http.js`
and `ws.js` point actual `/api`/`/ws` calls at the real `https://vaultapp.space`
so they fall through to the network instead of being claimed by Capacitor's
local asset loader. Full reasoning is in the comments in that file — read them
before touching `server.*` in the config, it's easy to "simplify" this into
something that looks equivalent and silently breaks login.

## Signing

```bash
keytool -genkeypair -v -keystore android_release.keystore \
  -alias vault-release -keyalg RSA -keysize 4096 -validity 10000 -storetype PKCS12
```

Run once, from the repo root. The keystore and its password
(`android_release.keystore`, `android_release.keystore.CREDENTIALS.txt`) are
gitignored and must be backed up somewhere durable (password manager, offline
storage) the moment they're created, same custody model as `vps_key.pem`.
**Losing this key permanently breaks updates for everyone who's already
installed the app** — Android refuses to install a same-`appId` update signed
by a different key, full stop, with no recovery path.

`android/app/build.gradle`'s `signingConfigs.release` reads the path/password/
alias from environment variables (`VAULT_ANDROID_KEYSTORE_PATH`,
`VAULT_ANDROID_KEYSTORE_PASSWORD`, `VAULT_ANDROID_KEY_ALIAS`,
`VAULT_ANDROID_KEY_PASSWORD`), never from a tracked file — same "secrets live
in the shell, not the repo" pattern as `ecosystem.config.cjs`. Built locally,
never on the VPS; the keystore and Android SDK never need to touch the server.

After building, sanity-check the result:

```bash
apksigner verify --print-certs android/app/build/outputs/apk/release/app-release.apk
aapt dump badging android/app/build/outputs/apk/release/app-release.apk | grep -E "package|application-icon"
```

## Distribution: self-hosted F-Droid repo

The app self-updates via a real F-Droid-protocol repo at
`https://vaultapp.space/fdroid/repo` — any F-Droid-compatible client (F-Droid,
Droid-ify, ...) can add that URL as a custom repo and gets normal update-check
and one-tap-install UX. This is **not** a submission to the official
f-droid.org repo: that would mean giving up this signing key and the whole
"build and publish it yourself" workflow in exchange for f-droid.org building
from source and reviewing every release. Two separate signing keys are in
play here, not one:

- `android_release.keystore` (repo root, gitignored) signs the **APK**.
- `deploy/fdroid/keystore.p12` (gitignored) signs the **repo index** — a
  completely different key, generated by `fdroid init`, that F-Droid clients
  use to verify the index itself hasn't been tampered with in transit.

Both need the same backup discipline as `vps_key.pem`. Losing
`deploy/fdroid/keystore.p12` means every client that's already added the repo
will reject the next index update as untrusted (same failure shape as an APK
signing-key loss, one layer up); nobody would be able to (re-)add the repo
under its old identity either.

### First: does this change need an app release at all?

Often it does not, and cutting one anyway has a cost — every installed app
prompts for an update.

`cap sync` copies `client/dist` wholesale into the APK, so the landing page is
bundled into every build. It is never rendered there: `App.svelte` branches on
`Capacitor.isNativePlatform()` and shows `NativeWelcome`, so `<Landing />` is
dead code on Android.

v1.42 and v1.43 were both landing-page releases. Each bumped `versionCode`,
signed an APK, published an F-Droid index and cut a GitHub release, and changed
nothing an Android user could see.

So there are two paths now:

```bash
# Website only — landing page, robots.txt, sitemap, nginx, OG image.
# No version bump, no APK, no F-Droid, no tag.
bash deploy/release-web.sh
```

It diffs against the last `v*` tag and refuses unless every changed path is on
its allowlist, so you do not have to make the judgement yourself. An
unrecognised path fails the check and sends you here, which is only slower.

Note what is *not* on that allowlist: `client/index.html` and
`client/src/main.js`. Both are the app's own shell and run on Android. That is
exactly why v1.44 was a full release while its two predecessors should not have
been.

Everything else — anything under `client/src` beyond `Landing.svelte`, anything
in `android/`, any dependency change — takes the full path below.

### Publishing a new release

```bash
cd deploy/fdroid

export JAVA_HOME="/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home"
export ANDROID_HOME="/opt/homebrew/share/android-commandlinetools"
export PATH="$JAVA_HOME/bin:$ANDROID_HOME/platform-tools:$ANDROID_HOME/cmdline-tools/latest/bin:$PATH"

# 1. Build + sign the APK (see above), then copy it in with the naming
#    convention fdroidserver expects:
cp ../../android/app/build/outputs/apk/release/app-release.apk \
   repo/space.vaultapp.messenger_<versionCode>.apk

# 2. Bump versionCode/versionName in android/app/build.gradle BEFORE building
#    (fdroidserver keys everything off the APK's own manifest, not a separate
#    version file), and update CurrentVersion/CurrentVersionCode in
#    metadata/space.vaultapp.messenger.yml to match.

# 3. Regenerate the icon set (see "A known rough edge" below) if this is a
#    release where the icon changed — otherwise the existing repo/icons*/
#    files are reused automatically since fdroid update only fills in what's
#    missing, it doesn't wipe what's already there.

fdroid update -c
fdroid update

# 4. Deploy repo/ to the VPS (see deploy/nginx/vaultapp.space.conf's /fdroid/
#    location) — e.g.:
rsync -avz --delete repo/ ubuntu@vaultapp.space:/home/ubuntu/VaultMessaging/fdroid/repo/
```

`deploy/fdroid/config.yml` (gitignored — it holds the index-signing key's
password in plaintext) is not reproduced automatically on a fresh machine;
`deploy/fdroid/config.yml.example` documents the non-secret settings
(`repo_url`, `repo_name`, `repo_description`) to reapply after a fresh
`fdroid init`.

### A known rough edge: the app icon needs manual help

`fdroid update`'s automatic per-app icon extraction reads raster PNG icon
files out of the built APK by filename. The release build here (AAPT2, no
`minifyEnabled`/`shrinkResources` involved) ends up with every launcher-icon
density resolving to a single compiled `res/BW.xml` — the debug build keeps
the normal `mipmap-*/ic_launcher*.png` files intact, so this is specific to
whatever optimization the release variant's resource linking applies; not yet
root-caused. Practically: the *installed app's own launcher icon* is
unaffected (confirmed on a real device) — this only affects the icon
fdroidserver would otherwise auto-populate into the repo listing.

The workaround, already applied once: `deploy/fdroid/icon.png` (tracked in
git — it's the same `logo.jpg` branding asset already at the repo root, not a
secret) is fdroidserver's *repo* icon source (its default `repo_icon: icon.png`
resolves relative to the working directory `fdroid update` is run from, not
`repo/icons/` — that asymmetry is what the comment in `config.yml.example`
is about). The *per-app* icon set
(`repo/icons*/space.vaultapp.messenger.<versionCode>.png`) was generated
by hand from the same source:

```bash
SRC=../../logo.jpg
APKID=space.vaultapp.messenger.<versionCode>.png
sips -s format png -z 512 512 "$SRC" --out repo/icons/$APKID
sips -s format png -z 192 192 "$SRC" --out repo/icons-640/$APKID
sips -s format png -z 144 144 "$SRC" --out repo/icons-480/$APKID
sips -s format png -z 96 96 "$SRC" --out repo/icons-320/$APKID
sips -s format png -z 72 72 "$SRC" --out repo/icons-240/$APKID
sips -s format png -z 48 48 "$SRC" --out repo/icons-160/$APKID
sips -s format png -z 36 36 "$SRC" --out repo/icons-120/$APKID
```

Only needed again if the icon changes or the `versionCode` in the filename
needs bumping — `fdroid update` won't overwrite icons that are already there
for a version it can't extract from, but it also won't rename them for a new
`versionCode`, so a version bump without a matching icon file just means that
one release shows no icon in v2-format clients until this is rerun.

### Get it into the official f-droid.org store

This is a separate, heavier track from the self-hosted repo above, and a
deliberate choice to make since it changes who signs the APK. Once accepted,
f-droid.org builds Vault from source on their own infrastructure and signs
with **their** key, not `android_release.keystore` — someone installing from
the official F-Droid app ends up on a different signature than someone using
the self-hosted repo, and Android treats those as incompatible updates (same
`INSTALL_FAILED_UPDATE_INCOMPATIBLE` behavior noted under Signing above). The
self-hosted repo keeps working unaffected either way; this just adds a
second, independent channel.

What official submission requires, and where this repo stands on each:

- **OSI/FSF-approved license with public source.** Done — `LICENSE`
  (AGPL-3.0-or-later), repo is public.
- **A reproducible build recipe** (`Builds:` metadata F-Droid's build server
  runs against a pinned commit, not a binary you hand them) — drafted at
  `deploy/fdroid/fdroiddata-submission/space.vaultapp.messenger.yml`. It
  chains `npm ci && npm run build && npx cap sync android` as a `prebuild`
  step ahead of the normal Gradle build, since the Android project depends on
  `client/dist` existing first. **Untested against F-Droid's actual
  buildserver image** — treat it as a first draft a reviewer will likely ask
  to adjust, not a finished recipe.
- **Fork `gitlab.com/fdroid/fdroiddata` and open a merge request** with that
  file at `metadata/space.vaultapp.messenger.yml`. This is a manual step:
  fdroiddata is GitLab-hosted, and this environment only has GitHub
  credentials configured, so it has to happen from an actual GitLab account.
  Steps: fork the project on GitLab, clone the fork, copy the drafted file
  in under `metadata/`, commit, push, open an MR against
  `fdroid/fdroiddata:master`. F-Droid's own submission guide
  (https://f-droid.org/docs/Submitting_to_F-Droid_Quick_Start_Guide/) covers
  the mechanics in more depth.
- **Volunteer review.** Anti-features, build reproducibility, and general
  fit get checked by F-Droid maintainers — commonly weeks to months, and
  near-certain to come back with requested changes to the `Builds:` recipe
  above.

## What's deliberately not automated

- No CI job builds this (`.github/workflows/ci.yml` stays client+server only)
  — `assembleRelease` correctness will silently rot unless built locally
  before each release.
- No emulator testing here — this was verified on a real device via `adb`
  and Chrome DevTools Protocol remote debugging, not a headless emulator.
- `fdroid lint`/`fdroid checkupdates` aren't run — this repo has one
  hand-built app, not a fleet of build-from-source ones, so most of what
  those commands check doesn't apply.
